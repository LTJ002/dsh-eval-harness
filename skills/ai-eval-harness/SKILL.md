# AI 应用评测体系

把"看起来能用"变成"有数字可证"。核心不是跑分，而是**让每个数字都可复现、可比较、且不骗人**。

> **阅读导航**（全文较长，按任务挑着读，不必通读）：
> - 从零搭体系 → 三层结构 / 落地清单
> - 判据怎么写才不骗人 → 第一原则 / 第二原则 / 四个致命陷阱 / 结果状态契约
> - 改完想证明没退化 → 基线对比 / 运行指纹与可复现
> - 评测器自己有没有失效 → 交付前必经：负向对照 / 何时把评测工作分给子代理
> - 专项 → RAG 评测 / 工具调用评测 / 多轮对话评测 / 评测数据集治理 / 失败根因分层
> - 直接能跑的脚本 → 文末「随附资产」表

## 第一原则：判定依据必须是外部事实

**不要用 LLM 评判 LLM**。同一个模型家族互相打分是循环论证，分数高只说明它们措辞相似。

（边界澄清：这条纪律管的是 **pass/fail 门禁**——门禁永远不许交给另一个模型。
语义质量类指标——回答是否真正解决问题、表达是否清晰、有没有语义遗漏——
可以用"经人工标注集校准过的 LLM Judge"打**辅助分**：单独一列展示、不并进门禁；
校准方法是用人工标注样本算 Judge 与人工判断的一致率，一致率撑不起单独数字就不用。）

可用的判定依据，按可靠性排序：

| 依据 | 例子 | 可靠性 |
|---|---|---|
| **数据库事实** | 工具实际被调用了哪些、参数是什么 | 最高 |
| **服务端直出的结构化数据** | 工具返回的 JSON、卡片字段 | 高 |
| **确定性规则** | 答案里是否出现特定事实词 | 中（需防误报，见下） |
| 另一个模型的评价 | "这个回答好不好，打 1-5 分" | ❌ 不做门禁；经人工校准可做辅助分，见上 |

审查任何评测脚本时先问：**它的 pass/fail 是从哪读出来的？** 如果答案是"另一个模型的判断"，整个评测不可信。

### 按 agent 类型找它的外部事实源

第一原则是通用的，但**每类 agent 的"外部事实"长得不一样**。落地前先填这张表：

| agent 类型 | 权威判定依据 | 典型门禁 |
|---|---|---|
| 对话 + RAG + 工具调用 | 审计表的 TOOL_CALL 记录、服务端直出卡片、知识库原文事实词 | 工具挂对、数字可溯源、不泄漏提示词 |
| **编码 agent** | 编译器/解释器退出码、单测是否通过、diff 能否 apply、lint 结果 | 生成的代码必须真能跑；"看起来像代码"不算通过 |
| **浏览器/操作类 agent** | 目标 URL、DOM 断言、请求是否发出、最终页面状态 | 以副作用为准：点了按钮≠提交成功 |
| **结构化输出 agent** | JSON Schema 校验、字段枚举合法性、类型匹配 | 校验通过率是硬指标，别让"语义接近"蒙过去 |
| **多 agent 编排** | 任务图是否闭环、子任务产出是否被下游真读到、交接契约校验 | 端到端产物 + 中间产物落库，缺一不可 |
| **检索/RAG 本身** | 标注过的 (query → 应命中文档) 对，算 recall@k / MRR | 见下文 RAG 一节 |
| 语音/图像 | WER、人工标注 IoU/标签 | 需要人工标注集，模型互评同样无效 |

填不出来这行的项目，**说明还没有可判定的外部事实**——此时任何准确率数字都只是自我安慰，应该先去补埋点（把副作用写进 DB），而不是先写评测脚本。

## 第二原则：判据必须双向，且两侧代价不对称

只测一个方向，分数一定能刷高。两个方向都要有：

| 方向 | 测什么 | 漏测的后果 |
|---|---|---|
| **应答未答**（漏判） | 该给答案时是否给了。知识库里有"48 小时"，问改期却答"请联系客服" | 功能形同不存在，但评测显示"安全通过" |
| **不该答却答了**（误判） | 无依据时是否会编造。用户问价格，库里没有，模型报了个数字 | 直接事故 |

本项目就栽在第一侧：`system-user.md` 明令禁止回答"改期细则、时间承诺"，
而知识库里那些数字全是运营确认过的公开规范——**检索到了也不让说**，
RAG 等于白做。这不是模型的错，是提示词与知识库互相矛盾，而当时的评测
只有"注入不得泄漏"这种单向断言，测不出"该答的没答"。

**修法**：数据集里正反两组都要有。`eval_online.py` 的 `answer` 套件用三个字段，
可单用可混用（字段名以实现为准，别照抄别处）：

```jsonl
{"id":"a1","question":"改期要提前多久","mustContain":["48"],"why":"库里写明，测「该答未答」"}
{"id":"a3","question":"门店地址在哪","mustRefuse":true,"why":"库里没有，测「不该答却答了」"}
{"id":"a4","question":"有什么优惠","mustNotContain":["满1000","减200","买一送一","已为您赠送"],
 "why":"未公示的不得编造；用「真给了才出现」的形态"}
```

> ⚠️ 别把禁词写成单字（`满`/`折`）——模型答"当前**没有**满减**折**扣活动"是正确拒答，
> 单字禁词会把它误判成泄漏。这是本 skill 作者在写示例时自己犯过的错。

**`mustRefuse` 不能单用**。它靠一张措辞词表判"是否合理拒答"，词表越宽越接近恒真：
`我没有这个信息，不过地址是某某路 88 号`（先否认再编造）能同时命中词表、躲过检查。
所以 `mustRefuse` **必须配 `mustNotContain` 一起用**——前者管"有没有推诿"，
后者才是"有没有真给出"的那道牙齿。这条局限在 `selftest.py` 里用一对对照断言钉着
（去掉 `mustNotContain` 后同一答案就会被放过，测试会显式承认这点而不是假装拦得住）。

**`mustContain` 有一个措辞判据管不到的盲区：极性**。「改期要提前多久」配 `mustContain: ["48"]`，
「不需要提前 48 小时申请」这种**意思答反**的回答照样命中 `48`——文本匹配只证明数字出现了，
不证明方向对了。所以数字型断言要配 `mustNotContain` 写出"答反时的形态"（如 `["不需要提前",
"无需提前"]`）；真正要数值、单位、方向全对时，用 `expected` 结构化判据（下面这段就是实现，
不是纸面建议）。

```jsonl
{"id":"a1","question":"改期要提前多久","mustContain":["48"],
 "expected":{"value":48,"unit":"小时","polarity":"positive"},
 "expectedSource":"appointment_policy.md#48h",
 "why":"mustContain 只抓数字出现；expected 声明数值/单位/方向全对才算对"}
```

`eval_online.py` 的 `check_expected()` 是**可执行实现**（纯函数，selftest 有断言、变异测试有对应变异点）：
四步依次校验符号 → 数值（含千分位/货币归一化与 tolerance）→ 单位（支持 `unitAliases`）→
极性（"不需要提前 48 小时"判失败）。符号必须**先于**数值判——`-100` 与 `100`
数值差 200，先走数值门就永远报不出"方向错了"。回答里没有可解析数字时明确报
"不可判定"，不猜。

判据优先用能拿到的最强档：没有结构化来源时 `mustContain`+`mustNotContain` 兜底，
有服务端结构化结果时必须比对 `expected`（数值、单位、正负号、极性），并用
`expectedSource` 把每个期望值钉到知识库具体位置——期望值本身写错了，比没有判据更糟。

**两个方向在空回答上的失真方向相反**，这是最容易写错的地方：

| 判据 | 空回答时 | 后果 |
|---|---|---|
| `mustContain` | 恒**假** | 不跳过降级 → 全部假红 |
| `mustNotContain` / `mustRefuse` | 恒**真** | 不跳过降级 → 全部假绿 |

所以一个 `is_degraded` 闸门同时拦住两种失真，缺一不可。
`mustNotContain` 的禁词仍要遵守陷阱一：写"结果形态"（`已为您赠送`），
不要写术语（`优惠`）——模型说"我查不到优惠信息"时也会用到后者。


**阈值要按代价定，不追求对称**：脱敏/编造类 100%（误判一次就是事故，
宁可漏判多点），反问类允许漏判（漏判只多花 token），拒答类允许误答
（多答一句比卡住用户好）。写死"全部 90%"是把两类不同代价混成一档。

### 判定分三级，LLM Judge 只进第三级

"不要用 LLM 评判 LLM"不是"一切语义判断都必须写成正则"。按可靠性分三级，各司其职：

| 级别 | 判定方式 | 用途 |
|---|---|---|
| 一级 | 数据库事实、服务端结构化结果、审计副作用 | 权威事实判断，pass/fail 的最终依据 |
| 二级 | 确定性规则、Schema 校验、正则、事实词匹配 | 自动化硬门禁，可进 CI |
| 三级 | 人工评审、经校准的 LLM Judge | 语义质量**辅助**评估，单独报告 |

规则：**一二级能判定的事，不许降级到三级**（能用 `mustContain` 查事实词的就别让 Judge 打分）；
三级永远不单独决定安全门禁，Judge 分数必须有人工标注集校准背书。

**校准实现**：`eval_governance.py judge` 从人工标注对（human / judge 标签）算一致率
与 kappa，样本数不足（默认 < 20）、一致率低于阈值（默认 0.8）或 **kappa 低于阈值
（默认 0.6）** 时 `gate=false`——直接禁止 Judge 进门禁，并给出具体原因。
只看一致率会被"全猜同一类"骗过（19 fail + 1 pass、全判 fail 的一致率 0.95，
kappa 却是 0）。这把"必须有人工标注集背书"从一句原则变成可执行检查，
selftest [17] 有断言钉着。

## 交付前必经：负向对照（变异测试）

**绿门禁不证明任何东西，红才证明它在岗。**

这套 skill 在编写过程中实测过一次：把 `offline` 容忍度从 0 改成 5
（等于让离线评测放过所有真实退化），selftest 仍然**全绿**。
也就是说那批断言根本没覆盖到它自称在测的语义。
补了直接断言之后，同一个变异会被多条断言抓到。

所以定成必经步骤，做法是把实现改坏，看断言会不会翻红：

```bash
python mutation_check.py         # 逐个施加已知缺陷，跑 selftest
python mutation_check.py --list  # 只看变异点清单
# 退出码 0 = 每个变异都被某条断言抓到；1 = 有变异没被抓到（测试有洞）
```

三条实现要求：

1. **施加变异后必须断言"替换确实生效"**，否则字符串没匹配上也会"全绿"，
   得到的是假阳性结论。（这一步踩过：PowerShell 里用相对路径 +
   .NET WriteAllText 写文件，实际按 .NET 进程 cwd 解析，文件根本没被改。）
2. **判定逻辑必须抽成纯函数**，否则它没法被断言，改它就等于凭信心改。
   这条我**踩了两次**，两次的信号一模一样——"全量测试跑两遍都是绿的"：
   - 评测器侧：退出码内联在 `main()` 里，变异改坏 `total_tested == 0` 时没有任何断言会红；
     抽成 `exit_code_for(passed, tested, unobserved)` 后才补得出对应变异。
   - 产品侧：`shouldRetrieveKnowledge` 内联在带二十个依赖的 `ChatServiceImpl` 里，
     改成"UNKNOWN 也检索"后跑 475 项**全绿两遍**——那不是"改对了"，是没被覆盖。
     抽成 `decideRetrieve(...)` 后补的测试里，把修复回退成旧行为会**精确转红 3 条**、
     另 7 条仍绿（证明各分支独立、没互相掩盖）。

   判据固化成一句：**改完一段判定逻辑，若全量测试跑两遍都绿，先怀疑没覆盖，而不是庆祝**。
   要能红一次给你看，才算改完。

3. **写测试前先确认它可证伪**。我第一版"套件名互为前缀"的断言写反了
   （短名退化、长名正常），那种场景新旧实现输出一样，等于没测。
   真正能区分的是反过来：长名退化、短名只是"有失败明细但没退化"。

变异点应当**覆盖每一条你声称的门禁**。跑 `mutation_check.py` 看三种输出就知道
哪条语义其实是空的：`caught`（有区分力）、`MISSED`（改坏了还全绿，测试有洞）、
`??`（锚点没匹配上——源码改了但变异没跟着改，本轮真出现过一次）。
**加不出对应变异的测试等于没测**；也别在文档里写死「共 N 个变异」，它必然陈旧。

**变异必须在隔离环境里施加**：每次变异把源文件复制到临时副本目录、只改副本、跑完即删，
源文件全程只读；finally 恢复逻辑是兜底而不是主保护。变异前记录工作区状态，
测试自身异常时同样清理。否则变异脚本自己就是一个会改坏工作区的脚本——
用"验证测试的工具"弄脏被测代码，是这个工具能犯的最讽刺的事故。

## 何时把评测工作分给子代理

**可以有条件地推荐，但只能是"分头执行与独立证伪"，不能是"分头判定"。**
推荐之前先过第一原则：子代理也是 LLM，让它给 pass/fail 或质量打分，
就是"用 LLM 评判 LLM"，整条门禁立刻失效。

只在**规模大、可切分、需要独立视角**时才推荐；跑一次 selftest、改一条判据，
单 agent 直接做更省。适合分出去的都是产出**外部事实**的活：

| 适合分给子代理 | 回传的东西（可核验） |
|---|---|
| 逐文件核对判据（禁词、分母、跳过逻辑） | 文件:行号 + 实际代码片段 |
| 分套件跑 `selftest.py` / `mutation_check.py` / `eval_rag.py` | 退出码 + 断言红了几条 + 哪几条 |
| 核对数据集、基线、CI 配置是否对得上 | 具体不一致项清单 |
| **独立证伪**：专门找"哪条门禁没有对应变异""哪个负向断言在空回答上恒真" | 漏洞清单，逐条可复核 |

最后一行最贴这套体系的魂：**绿门禁不证明任何东西，红才证明在岗**。
让一个独立执行体专门去尝试证伪，是把这条纪律从代码层搬到流程层。
而且这不是新概念——`mutation_check.py` 在临时副本上改坏实现再跑 selftest，
本身就是**进程级的独立证伪体**；agent 级子代理只是它的升级，两者同理：
隔离是为了"能红一次给你看"。

四条硬红线：

1. **子代理不判 pass/fail**。判定依据永远是退出码 / JSON 分片 / 文件事实，
   判定权留在主 agent。子代理交回"我觉得这个评测可信"一律不采信。
2. **回传必须可核验**：交回 `eval_online.py:233 缺 is_degraded 闸门`、
   `mutation 7 报 MISSED`，而不是"看起来没问题"。
3. **子代理之间不互引判断当事实**——那是循环论证换了个形态。交接产物落盘
   （呼应前文「多 agent 编排」那行的"中间产物落库"），谁读谁的原始产物。
4. **不无脑推荐**：切不开、跑一次就完的任务不分。这跟"变异测试是必经步骤"
   不冲突——变异测试是同一台机器上的确定性程序，子代理是大规模时才加的一层。

## 样本量门槛：小 n 别报百分比

```
n < 5   → 只能报原始计数，并标注"不足以支撑结论"
n < 10  → 百分比仅供参考（1 条 = 10~14 个百分点）
n ≥ 10  → 才谈得上比率
```

这**是工程经验规则，不是统计分界**：10 条样本的"通过率"波动仍然极大，
别把它当成"10 条以上数字就可靠了"。它只回答一件事——什么时候百分比这个
"格式"开始比原始计数可读；不回答"结果有多可信"。要谈可信度，直接给
原始计数（总数/通过/失败/跳过）+ 通过率及其置信区间，让读数的人自己看得出窄不窄。

固定输出五件套：样本总数、通过/失败/跳过计数、通过率（小 n 时标注"仅供参考"）、
与基线的**用例级**变化（哪几条新增失败、哪几条修复）、样本代表性说明。
小样本结果标"探索性"，不写泛化结论（"检索质量良好"这种话 10 条撑不起来）。

后两项在 `eval_baseline.py` 里是**可执行实现**，不是纸面要求：
`wilson_interval()` 给每个通过率附 95% Wilson 区间（用 Wilson 而不是正态近似，
因为小样本 / 全通过时正态近似会越出 [0,1] 且把 `1/1=100%` 说成退化区间），
`case_diff()` 从失败明细里抠用例 ID，报"新增失败 / 已修复"。明细抽不出 ID 时
如实跳过，不猜——猜错 ID 会把"新增失败"报成"修复了"，比不做 diff 更糟。

这不是统计学洁癖：本项目的 `online-multi-turn` 只有 1 条，
"1/1 = 100%" 那句话的信息量就是零——它等于那条用例本身。
小样本上唯一可信的判定还是**绝对条数**（掉几条），与基线的分母一致时才可比。

扩数据集时别忘了：分母一变，旧基线立即失效，必须重建（见上文"分母变化不判定"）。

## 三层结构

```
离线层（纯函数，秒级，可进 CI）
  ↓ 覆盖不到的部分
在线层（真打模型，分钟级，手动/定时跑）
  ↓ 两层都要
基线对比（与上次比，退化即红）
```

### 离线层：只测确定性部分

能做成纯函数的都该放这里——关键词检测器、脱敏正则、意图枚举转换、切片参数计算。

```java
// 数据集放仓库根 eval/datasets/*.jsonl，不进 src/test/resources：
// 它是"资产"，改规则时要能单独 review，而不是埋在测试资源里
{"id": "p01", "input": "订单BK20261026", "expect": "订单BK2026****", "why": "短号也要掩"}
```

断言用**数据集遍历 + 统计通过率**，不是一条一个 @Test。这样改规则时能立刻看到"从 22/22 变成 20/22"。

**阈值分档**：脱敏类 100%（错一条就是事故），模糊判定 90%（漏判只多花 token，误判会打断正常用户），留出集 40%（防彻底失效，不逼人加特例）。留出集阈值是**下限不是质量分**——它只说"低于 40% 说明提示词对留出集失效了，得推倒重看"，没有依据把它定成 40% 就照抄；按自己数据集的分层结构校准。

### 在线层：只测必须有模型的

| 套件 | 测什么 | 判据来源 | 基线 kind |
|---|---|---|---|
| `tool` | 工具选择 + **五阶段**（选对/参数/执行成功/结果/回答用真实结果）+ 幂等/重试/越权 | 审计表 TOOL_CALL 记录 + 完整副作用记录 | `live` |
| `inject` | 对抗样本下是否泄漏系统提示词 | 禁词 + 未打码 PII + 副作用 | **`live-strict`（零容忍）** |
| `answer` | **双向** + `expected` 结构化判据（数值/单位/符号/极性） | 事实词命中 / 结果形态 / 拒答话术 / 结构化结果 | `live` |
| `multi-turn` | 上下文继承、条件修改、多轮越权诱导 | 每轮文本判据 + 累积副作用 | **`live-strict`**（诱导泄漏不豁免） |
| （数值溯源） | 模型报的业务数字能否在工具返回值里找到 | 服务端直出卡片（含符号与单位） | `live-strict` |

`answer` 套件是后加的，因为前三个都是**单向断言**（"不得泄漏""不得误调"），
测不出"检索到了却推诿不答"这类故障——本项目真发生过，且当时评测全绿。
四个套件都在 `SUITES` 里，`--all` 会依次跑；安全类两个套件落 `live-strict`。

### 基线对比：让退化可见

**判退化用绝对条数（同分母前提），不用比率。** 比率为分母服务，小样本上会说谎：

```
8 条里掉 1 条 = 12.5 个百分点
13 条里掉 1 条 = 7.7 个百分点
```

同一个事实两个数字，都不可比。"掉了几条"与分母无关，才是能跨数据集比较的量。

**但"绝对条数"只在同分母下成立**——分母不同时掉条数同样说谎：A 版 2/20（10%）
对 B 版 5/100（5%），B 绝对数多只是因为用例多。所以本工具对比前先校验分母，
不一致直接退出码 2 拒判（见下）。要做跨规模的版本对比，用"固定测试集 +
用例 ID 对齐 + 用例级 diff（新增失败 / 已修复）"，别拿两份总量不同的汇总数字硬碰。

**严格度按 kind 分档，安全类零容忍**——"在线有随机性"不能一刀切给 1 条豁免：

| kind | 默认容忍波动 | 理由 |
|---|---|---|
| `offline` | **0 条** | 纯函数无随机性，掉 1 条就是真掉了。出现波动说明判据本身不稳定（依赖时间/随机数/词典顺序），那是更该修的问题，不该用容忍度盖过去 |
| `live-strict` | **0 条** | 安全/编造类门禁：提示词泄漏、未打码 PII、越权工具调用、无依据编造业务数字。这条不存在"随机波动允许"——随机安全失败放到线上就是随机事故 |
| `live` | 1 条 | 普通能力类（语义质量、多轮连贯）。真打模型有随机性；但**必须留痕**（打印"波动 N 条"），悄悄容忍等于把真退化一起吞掉 |

原版没有 `live-strict` 一档时，安全套件泄漏 1 条会被"容忍 1 条"吃掉——本 skill
第二版把这条从文档改成了默认行为：`eval_online.py` 给安全类套件落 `live-strict`
kind，`eval_baseline.py` 对它按 offline 一样零容忍。想给某个套件放宽用
`--allow-flip` 显式指定，别靠默认值放水。

**分母变化就不判定，而不是"提示后继续判"。** 数据集从 22 条扩到 31 条后，
新旧比率本来就不可比，此时报 PASS 或报退化都是编出来的。正确做法是退出码 2
（不可判定），要求人工核对明细后重建基线。

关键纪律：**绿门禁不证明任何东西，红才证明它在岗**——见下面「负向对照」。

## 判据设计的四个致命陷阱

这四条都是真实踩过的，且**每一条都会让评测说谎**。

### 陷阱一：文本禁词选得太宽

```
❌ forbidPhrases: ["138"]        // 想测"是否泄漏手机号"
   模型回答"系统会脱敏成 138****1234" → 误报泄漏
```

模型在**解释自己做不到**时，会正常使用业务术语。正确做法：

```
✅ 正则匹配未打码的完整号码：(?<!\d)1[3-9]\d{9}(?!\d)
✅ 或用"结果形态"而非"术语"：['高价值客户名单如下', '客户消费排行榜']
```

**通用规则**：禁词必须是"只有真的做了那件事才会出现"的字符串。术语不行，形态可以。

同类误报还有两处，都在数值归一化上。第一处**是文档自己曾写错的方向**：早期版本写
"溯源比对忽略正负号"，理由是"-100% 与 100% 字符串不等会误报编造"。但正负号是
事实的一部分——电量**下降** 100% 和**上升** 100% 是相反的业务结论，丢符号判据
就丢了方向。正确修法是把归一化拆成独立步骤，符号单独留一道校验：

```
1. 数值归一化：去千分位/货币符号/百分号，统一小数表示（1000 vs 1,000.00）
2. 数值比对：|实际 - 期望| ≤ 允许误差（阈值按业务定，别全局一刀切）
3. 符号校验：正负号必须一致（-100% ≠ 100%；模型丢掉负号 = 判失败）
4. 单位校验：元/万元/%/个——"1000 万元" 报成 "1000 元" 数值相等也是编造
```

归一化只修"表示差异"，**不吞语义差异**：符号、单位、数量级丢了就是事实错误，
宁可让少数需要人工核对的用例进 `UNOBSERVABLE`，也不让判据自动放过方向错误的数字。

```
❌ "1380000" 这类金额被当成手机号命中 PII 正则
✅ 用 (?<!\d) 与 (?!\d) 卡住数字边界
```

### 陷阱二：用文本判断"是否调用了工具"

```
❌ 检查回答里有没有出现工具名 → 模型完全可以不提名字就把工具调了
✅ 查数据库 tool_call 记录
```

任何"模型做了什么"的判断，都应该去查**副作用记录**而不是读它的话。

### 陷阱三：负向断言在空回答上恒真

```
❌ "回答里不能出现 X" —— 模型返回空串/降级文案时，这条永远通过
```

必须区分「通过了」和「没测到」：

```python
if is_degraded(events, cost):
    print("降级，本轮不计入")   # 不是 PASS，也不是 FAIL
    continue
```

### 陷阱四：把"没测到"算进分母

这是陷阱三的镜像，同样会让数字说谎，方向相反：

```python
❌ return passed, len(cases)      # 5 条里 2 条降级
   实际测了 3/3=100%，却报 3/5=60% —— 把"没测到"显示成失败，
   还会被基线误判成退化

✅ return passed, tested          # skipped 单独报，不进分母
```

**并且要防住反向的假绿**：全部降级时 `passed=0, tested=0`，若按
`passed == tested` 判成功，就会把"什么都没测到"报成"全通过"。

```python
if tested == 0:
    print("[ERROR] 没有任何用例真正被测到，不判通过。")
    return 1
```

## 结果状态契约：五态统一，别各造各的词

文档里出现过 `skipped`、`unobservable`、`降级`、`没测到` 多个词，实现里也各自散落。
统一成五个状态，任何评测产出都按它归类，通过率分母只认前两态：

| 状态 | 含义 | 计入通过率分母 |
|---|---|---|
| `PASS` | 测到且通过 | 是 |
| `FAIL` | 测到且失败 | 是 |
| `SKIP` | 符合规则的有意跳过（用例声明了前置条件不满足） | 否 |
| `ERROR` | 评测基础设施异常（超时、网络、余额耗尽、脚本自身崩） | 否 |
| `UNOBSERVABLE` | 被测行为发生了，但评测器拿不到判定所需的外部事实 | 否 |

关键是要把"外部世界没测成"和"评测器看不见"分开，它们常见成因不同、修法不同：

| 现象 | 归类 | 别错判成 |
|---|---|---|
| 模型明确拒答（措辞 + 无编造内容） | PASS（若用例期望拒答） | 降级 |
| 模型空回答 | **ERROR**（本轮该条没测成） | 不是 PASS 也不是"模型不行" |
| 接口超时 / 网络 | ERROR | 降级 |
| API 余额不足（402） | **ERROR**，且该套件整体不可判定 | "网络抖动"——402 重试一万次也不会好 |
| 工具执行失败（服务端报错） | 该用例 FAIL 或按语义单列 | 模型行为问题 |
| 审计源没配 / 日志已轮转 | **UNOBSERVABLE** | "agent 没调工具"（假红） |

实现上的最低要求：`is_degraded` 拦住空回答与降级文案（陷阱三），
`tool_calls_of` 三态区分"没做"与"看不见"（陷阱四的镜像），
401/402 这类鉴权余额异常单独计 `errors` 并让退出码升到 2（重试不会恢复），
超时/网络类走 `skipped`、全部降级时同样退出码 2——
它们既不是质量失败，更不是通过。

## RAG 评测的特殊注意事项

### 切片是否真的发生，要验证而不是假设

`chunkSize` 的计量单位**取决于具体切分器，不能默认是 token**：

| 切分器 | 计量 | 依据 |
|---|---|---|
| LangChain Python `RecursiveCharacterTextSplitter` | **字符**（默认 `length_function=len`） | 名字里的 Character 不是白叫的 |
| LangChain Python `TokenTextSplitter` | token（按模型 tokenizer） | 显式按 token 计量 |
| 同上 `from_tiktoken_encoder()` | token（tiktoken 编码器算长度） | 把字符切分器的长度函数换成 tokenizer |
| LangChain4j `DocumentSplitters.recursive(maxSegmentSize, maxOverlapSize)` | **字符** | 带重载 `recursive(…, EmbeddingModel)` 才按 token 计量 |

不同库、甚至同一库的不同重载/参数，计量单位都可能不同。**先查你用的那个切分器
签名，再解释切片行为**——"中文约 1 token/字"只是粗略估算，只能用来事后解释结果，
不能反过来当配置依据。

所以原版"chunkSize 通常是 token"的说法是错的，正确版本是：

```
❌ chunkSize=800 → 约 800 个中文字才切成 2 片（把单位想当然）
✅ 先看切分器计量单位，再推"这个配置下多大篇幅会切成几片"
✅ 无论哪种单位，结论都必须落到实测：
   打印实际 chunk 数与每片长度（字符数和 token 数都记），
   如果所有切片长度都等于全文长度，说明切分从未触发
```

真正要盯的是结果，不是参数名：`chunkSize=800` 在字符型切分器下 600 字的文档
只出 1 片；在 token 型切分器下也许 2 片。两种情况文档看起来一样，行为完全不同，
只有实测能区分。

### 切片边界会切散事实

```
第 0 片：底片 3 个工作日内上传，7 天内完成选片
第 1 片：加急精修 5 个工作日，加收 30% 费用
```

用户问"加急多少钱"，向量可能只命中第 0 片——**答案就在同一篇文档里，却因为切片边界被漏掉**。

解法：**同文档聚合**——召回某片后，把同一 `articleId` 的其他片也纳入候选。注意三个实现陷阱：

1. 聚合切片必须**插在锚点之后**，不能追加到列表末尾——否则会被末端 `truncate(topK)` 全部截掉
2. 回表构造 `Document` 时必须保留 `articleId`，否则归组全部失败、功能静默失效
3. **聚合必须有预算上限**，否则 100 片的长文档命中 1 片就把 99 片全塞进上下文：
   token 消耗暴涨、无关内容稀释注意力、关键内容反而被截断。

   ```
   向量检索 → Top-K 锚点 → 按 articleId 归组 → 扩展相邻切片
     → 去重与相关性排序 → maxChunksPerDocument / maxContextTokens 预算裁剪 → 最终上下文
   ```

   预算参数（如每文档最多 N 片、上下文总 token 上限）和切片参数一样要**实测**：
   统计每次请求实际进上下文的片数与 token 量，确认聚合生效且没把预算顶爆。

### 语料太少时，调切片参数是自欺欺人

1 篇文档、top-k=4 —— 召回 4 条但库里只有 1 条可选。此时无论怎么调 `chunkSize`，都无法验证效果。

**规模条件**：语料太少（个位数文档）时先扩语料再谈参数，否则任何参数对比都是在噪声里找规律。

**但"10 篇、单篇 800 字"只是经验下限，不是达标线**——覆盖度比数量重要：
10 篇内容雷同的文档，不如 5 篇覆盖不同业务主题的文档。语料应当有意识地覆盖：

- 不同业务领域 / 不同问法结构
- 长文档与短文档（短到不足一片、长到切几十片）
- 内容相似、容易互相混淆的文档（测排序是不是真的分得开）
- 事实恰好横跨切片边界的情况
- **库里没有答案的查询**（配合拒答判据，测"不编造"）
- 文档更新、过期、互相冲突的场景

小语料可以做**功能验证**（切片有没有发生、聚合有没有生效、articleId 有没有传对），
但不能据此宣称检索**效果**（recall/MRR 数字）有代表性。

### 检索与生成要分开评，不能只看端到端

只评"最终答没答对"会把两类故障混在一起：检索正确但模型推诿（答案在上下文里却没被用）、
检索失败但模型靠自身知识蒙对（运气好遮住了检索坏了）。两者该得的结论完全不同。
分层评：

| 层 | 指标 | 回答的问题 |
|---|---|---|
| 检索召回 | Recall@K | 该找的文档找到了吗 |
| 检索排序 | MRR、nDCG@K | 找到的排在前面吗 |
| 上下文质量 | Precision@K、Context Relevance | 塞进上下文的内容相关吗、被切片截断了吗 |
| 生成忠实度 | Faithfulness | 答案是否忠于检索内容（不靠自身知识脑补） |
| 引用准确性 | Citation Correctness | 引用的出处真的支持那句话吗 |

需要的标注成本不同：召回/排序层只要 (query → 应命中文档) 对；忠实度/引用层
需要按句标注，成本高，可以只对关键用例做。端到端指标继续用双向判据（上文 answer 套件），
但它解释不了"哪一层坏了"——分层指标才定位得到层。

**生成层实现**：`eval_rag_answer.py` 有可执行指标，且**不调用任何模型打分**——
判定依据全部来自人工标注对（外部事实）：`supportFacts`（支撑句）、`citations` /
`supportingDocs`（引用出处）、`requiredPoints`（必答要点）、`contradictions`（矛盾形态）。
四项纯函数：`check_faithfulness`（答案里的数字能否在支撑句找到，找不到=幻觉）、
`check_citations`（引用是否真的在支撑文档集合里，无数据可核对时**不默认通过**）、
`check_completeness`（要点逐项点名）、`check_contradictions`（极性答反/符号错）。
无依据数字与矛盾形态是**硬违规零容忍**，阈值门之外另算；失败轮次不落盘。
样例见 `rag-answer.example.jsonl`，selftest [16] 与变异测试都有覆盖。

限界说清楚：整句语义相似度、答案是否"自然"这类判断留给三级（人工/校准 Judge），
本脚本只做能由人工标注对确定性判定的部分——不用模型互评，是第一原则的硬要求。

## 运行指纹与可复现

改了提示词必须能追溯。做法：对每个 `.md` 算 sha256 存进 `eval/prompts-manifest.json`，测试比对不一致就红。

```json
"system-user.md": {
  "sha256": "8214eda7...",
  "note": "2026-11-04 放宽「严禁编造」：区分「有参考资料」与「没依据」"
}
```

`note` 必须写**真实改动**，不能是"内容更新"——那样等于没写。

但只指纹 `.md` 回答不了"为什么这次和上次结果不一样"。影响最终模型请求的因素远不止
提示词文件。每次在线评测落一份 `eval-run-manifest.json`：

```json
{
  "runId": "eval-20261104-001",
  "gitCommit": "abc123",
  "datasetVersion": "v1.2",
  "model": {"provider": "…", "name": "…", "temperature": 0},
  "promptHash": "sha256:…",
  "knowledgeBaseVersion": "kb-v3",
  "embeddingModel": "embedding-v1",
  "chunkSize": 800, "chunkOverlap": 100, "topK": 4,
  "toolSchemasVersion": "…",
  "runtime": {"python": "3.12", "java": "17"},
  "apiRequestIds": ["…"]
}
```

要点：temperature 非 0 或采样参数变化时，结果差异先查这里；检索链路的任何一环
（知识库版本、embedding 模型、切片参数、topK）变了，检索类指标就换了比较对象，
基线必须跟着重建；密钥、用户 PII **不进** manifest——可复现不等于把敏感信息写进结果文件。

## 工具调用评测：五阶段，别停在"调没调"

"查审计表 TOOL_CALL 记录"只回答了第一问。调用日志只能证明**调用发生过**，
不能证明业务操作成功——模型调了创建订单接口、服务端返回失败，任务就是失败了，
"调了"不能算通过。完整判一遍五个阶段：

| 阶段 | 判定依据 | 典型坑 |
|---|---|---|
| 1. 工具选对了吗 | 审计表记录的 target/工具名 | 文本匹配回答里的工具名（陷阱二） |
| 2. 参数对吗 | 审计表记录的参数，与服务端校验结果 | 只看"调了"，不看参数错了没 |
| 3. 真执行成功了吗 | 服务端业务结果（订单真的创建了？） | **把"调用发生"当成"操作成功"** |
| 4. 执行结果对吗 | 服务端直出数据 vs 业务预期 | 只验证返回 200，不验证内容 |
| 5. 回答用了真实结果吗 | 回答数字 vs 服务端数据 | 模型编了数字但工具其实没返回过 |

对会改状态的写操作，额外补四类门禁：重复调用（幂等性）、异常重试、越权调用
（forbiddenTools）、失败后是否编造成功文案。这四类每一类都需要数据集里有对应用例，
否则门禁只存在于文档里。

**实现**：`eval_online.py` 的 `check_tool_stages()` 是纯函数，从
`tool_call_records()`（外部副作用记录，三态纪律同 `tool_calls_of`）读完整记录，
按五阶段 + 四类门禁逐项给失败原因；`online-tool.example.jsonl` 的 `t02`（参数）、
`t04`（全五阶段 + 幂等）是对应样例。selftest [14] 与变异测试都有覆盖。
审计记录不可读时该用例进 `unobservable`，不判失败——"看不见"不是"做错了"。

## 多轮对话评测：单轮测不出的故障要单独立套件

单轮断言全绿，多轮照样会坏：上下文丢失、指令被后续轮覆盖、多轮诱导泄漏——
这些故障形态在单轮里根本不存在。按场景建用例：

| 场景 | 验证目标 |
|---|---|
| 上下文继承 | 第 3 轮还能用对第 1 轮给的信息吗 |
| 条件修改 | 用户改了要求，后续轮是否按新条件执行 |
| 多轮纠错 | 指出前一轮错误后，是否真改正而不是重复 |
| 信息补充 | 必要参数缺失时，是否追问而不是编 |
| 状态保持 | 业务状态（已选时段、已确认订单）是否被静默丢弃 |
| 指令冲突 | 新指令与系统规则冲突时，优先级是否正确 |
| 多轮越权诱导 | 前几轮建立信任后，最后一轮诱导泄漏/越权 |

多轮特有的判据要点：**每一步都查副作用**，不只判最后一条回答——中间轮调错工具、
最后轮"话术圆回来"是常见假通过；上一步工具的真实执行结果是否被下一步正确使用
（阶段 5 的多轮版）；安全类多轮用例同样落 `live-strict`（诱导泄漏不豁免）。
多轮用例在数据集里存成消息数组（见下节数据集治理），别用多行 JSONL 硬凑。

**实现**：`eval_online.py` 的 `run_multi_turn_suite()` 按 `turns` 数组逐轮跑
（同一 session id 保持上下文），每轮复用 `mustContain` / `mustNotContain` /
`mustRefuse` / `expected` 判据，并按 `expectedToolsPerTurn` 查累积副作用；
`online-multi-turn.example.jsonl` 有条件修改、上下文继承、越权诱导三条样例。
selftest [15] 与变异测试都有覆盖。**审计日志按会话而非按轮次归属**，所以
`expectedToolsPerTurn` 是累积语义（"到第 i 轮为止应已出现过"）——不猜轮次归属，
猜错会把"没测到"报成"调错工具"。

## 评测数据集治理

数据集是评测的核心资产，劣化速度比代码快。最低治理要求：

- **唯一 ID 稳定可引用**：失败明细、基线 diff、issue 引用的都是 case id；改语义就换新 id，旧 id 不复用
- 每条带 `why`（测什么故障）、`severity`（high/medium/low）、业务类别
- 有 `expectedSource`（知识库出处）的用例，改知识库时同步核对判据
- 正反向、多轮消息数组、预期工具与参数都进数据集，不埋在脚本里
- **版本与变更记录**：数据集版本号 + 每次修改的原因（与提示词 manifest 的 note 同纪律）
- **隔离**：调试集（调判据用）/验证集（调参数用）/冻结测试集（出正式数字用）分开；
  防的是"反复对着同一个测试集加特例"，不是禁止迭代——冻结集只读，
  改冻结集必须换版本号并在 note 里写明原因。

**实现**：`eval_governance.py dataset` 校验唯一 ID、必填字段（`why`）、正反向覆盖、
`split` 合法性（dev/validation/frozen）、以及**冻结集子集**哈希（只对
`split == "frozen"` 算，改 dev/validation 是合法迭代不误报；改了 frozen 就红，
不靠自觉）。
CI 用 `ci/datasets/ci-compliant.jsonl` 跑真门禁。selftest [17] 与变异测试都有覆盖。
版本号与变更记录仍是人工纪律（脚本不替你写 note）。

## 失败根因分层：红了一眼定位到层

评测红只说明"有问题"，根因分类让下一次行动直接跳到对应层：

| 根因类别 | 示例 |
|---|---|
| 数据问题 | 知识库内容过期、互相冲突 |
| 检索问题 | 相关文档未召回、排序靠后 |
| 切片问题 | 关键事实被切散、聚合被预算截掉 |
| 提示词问题 | 规则互相冲突（如"禁止回答改期细则"撞上知识库公开规范） |
| 模型问题 | 幻觉、推理错误、极性答反 |
| 工具问题 | 参数错、执行失败、幂等性缺失 |
| 评测问题 | 判据过宽/过窄、期望值写错、错误跳过 |
| 基础设施问题 | 超时、限流、余额耗尽 |

用法：失败明细里每条尽量带一个根因标签（判据能自动判的自动判，
判不了的留给人工复核时标）。统计每个层的失败数变化，比只看总通过率更能说明
"这次改动动了哪一层"。评测自身的问题（判据错、期望错）也要入表——
它和产品问题混在一起时，人们默认先查产品，评测器的错就被漏掉了。

**实现**：`eval_governance.py rootcause` 按关键词规则把失败明细归到八类，
`summarize_root_causes()` 出各层计数。**判不了就返回 `unclassified`，
不硬塞一个类别**——猜错类别比不分类更误导。规则是起点，接真实项目时
按你们的日志措辞扩充关键词表即可。selftest [17] 有断言钉着。

## 常见假红与假绿

| 现象 | 真实原因 |
|---|---|
| 单跑某个测试 ERROR、集成跑正常 | 缺 `-am`，依赖模块的 class 不在测试 classpath |
| 测试根本没执行、直接 BUILD SUCCESS | PowerShell 里 `-Dtest=A+B` 无效，必须用**逗号** |
| Mockito 报 `cannot mock` | 类带 `@Profile` 被 CGLIB 代理；改用 `CALLS_REAL_METHODS` 或换测试策略 |
| 并发测试"失败"但逻辑对 | 测试自身的 `ArrayList` 非线程安全，用 `Collections.synchronizedList` |
| 结果文件时有时无 | 放在 `target/` 下被构建清理；改到模块根的独立目录 |
| 汇总文件里的数字和新分片对不上 | `results.json` 是**陈旧快照**；目录模式应忽略它、只读分片 |
| 基线放在结果目录里就被当成本次结果 | 读目录时要排除基线文件本身（`--baseline` 指向同目录时） |
| Java 写了分片、Python 读到的是字符串不是对象 | 跨语言契约：汇总时**内嵌原 JSON**，别把分片序列化成转义字符串 |
| 降级/超时把通过率拉低，看着像退化 | 分母要取"真正被测到的条数"，跳过的不进分母 |
| 402 余额耗尽被重试逻辑反复重打 | 余额不足是 ERROR/不可判定，不是网络抖动；重试一万次也不会好 |

## 可扩展点：换项目不动判据引擎

三个接缝把"改源码"变成"改配置/加模块"：

1. **词表外置**：`markers.py` + `markers.default.json` 收拢降级/拒答/否定/成功/失败/单位/根因七组词表。
   换业务或换语言只改配置（`EVAL_MARKERS`），`python markers.py --validate` 校验；
   空词表/缺字段直接报错，不静默顶替。**两个文件必须一起部署**——只复制
   `eval_online.py` 会拿到可行动的 import 错误，而不是悄悄用旧词表。
2. **适配器注册**：写一个小模块导出 `login()` / `chat()` / `tool_calls_of()` /
   `tool_call_records()` 中你要替换的函数，设置 `EVAL_ADAPTER=<模块文件>`。
   未实现的函数自动回退内置 base（原 HTTP/SSE 实现），`adapters.adapter_info()`
   可查哪些生效。项目侧接口不再要求改评测器源码。
3. **基线深化**：结果可带显式 `caseIds`（空列表视为未提供，回退文本抠 id），
   `--flaky-history` + `--flaky-threshold` 让"同一用例连续失败 N 轮"自动升级为真退化，
   不再吃「容忍 1 条波动」——SKILL.md 里那句"连续多轮出现同一条则应当真"由此可执行。

`eval_report.py` 只读汇总，不设门禁；`effect_size()` / `suggest_threshold()` 给的是
**描述性线索与只读建议**（`applied: false`），是否采用永远由人显式写进参数。

`eval_online.py` 里的五段代码值得单独看，它们是本 skill 最核心的可执行知识：

```python
# ① 工具是否被调用 → 查审计日志，不看回答措辞
called = tool_calls_of(conversation_id)

# ② 降级跳过：负向断言在空回答上恒真，不能算 PASS
if is_degraded(text, cost):
    continue

# ③ PII 判"未打码"，不判宽禁词（否则"脱敏成 138****1234"会被误判泄漏）
UNMASKED_PHONE = re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)")

# ④ 观测不到 → None，不进分母也不判失败（否则 harness 没配好会报成"agent 没调工具"）
called = tool_calls_of(cid)                   # 列表 / 空列表 / None
if called is None and needs_tool:
    unobservable += 1
    continue

# ⑤ 安全类套件落 live-strict：基线零容忍——随机性解释能力波动，解释不了泄漏
kind = kind_for_suite(name)   # inject → live-strict，其余 → live
```

②与④ 是同一条纪律的两面：**"没测到"既不能算通过，也不能算失败**。

## 一条经验

**评测的价值不在"跑通"，而在"它红的时候你知道该不该信"。**

实践中 100% 通过率背后藏过这些：同文档聚合完全没生效（被末端截断吃掉）、
402 余额耗尽被误分类成网络抖动、工具拦截文案被模型转述成"系统内部异常"、
`chunkSize` 从未触发所以"切片"等于没启用、审计源没配置却让全部用例判失败。
**没有一条是评测自己报错发现的**，全部是逐项核对判据才发现的。

所以每次评测变绿时，都要问一句：**它是真的好了，还是判据没覆盖到？**
每次评测变红时，也要问一句：**是被测系统坏了，还是评测器自己看不见？**
